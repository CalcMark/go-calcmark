# Phase 11.1: Bug Fixes - Research

**Researched:** 2026-02-07
**Domain:** Interpreter correctness and TUI editor interaction bugs
**Confidence:** HIGH

## Summary

Phase 11.1 addresses five specific bugs discovered during v1.1 development: convert_rate preview display, delete character behavior, preview pane blank lines, and preview pane markdown filtering. The research focused on understanding the TUI testing framework (catwalk), the interpreter's rate conversion logic, the delete key handling in the editor, and the preview pane rendering pipeline.

**Key findings:**
- Catwalk provides data-driven testing for Bubbletea TUI models with multiple observers (debug, view, results, lines)
- The project already has extensive test infrastructure for TUI bugs using catwalk in testdata/ directories
- Delete key bug has existing test file (delete_single_char_test.go) that reproduces the issue
- kb/KB unit handling uses binary (1024-based) interpretation, which is correct but may cause confusion
- Preview pane rendering uses block_render.go and aligned.go for markdown filtering

**Primary recommendation:** Use test-driven approach with catwalk tests for TUI bugs and table-driven tests for interpreter bugs. Each bug must have a failing test before the fix.

## Architecture Patterns

### Pattern 1: Catwalk Test-Driven Bug Fixing
**What:** Write catwalk test that reproduces the exact key sequence triggering the bug
**When to use:** Any user-facing TUI bug (delete, navigation, rendering)
**Example:**
```go
// In testdata/delete_last_char:
# Reproduce user scenario: type 'a', move left, press DELETE
run observe=debug
type a
key left
key delete
----
-- debug:
cursorLine=0 cursorCol=0 editBuf=""
```

**Key principle from TESTING.md:**
> Every user-facing TUI bug MUST have a catwalk test that:
> 1. Reproduces the exact key sequence that triggered the bug
> 2. Asserts on the buggy behavior (to verify the bug exists)
> 3. After fixing, the test asserts on the correct behavior
> 4. Prevents regression

### Pattern 2: Isolated Unit Test for Delete Bug
**What:** The delete_single_char_test.go file already exists with 7 test scenarios
**When to use:** When debugging the transitionToEditing() reload issue
**Example:**
```go
// TestDeleteSingleChar_InitialCursor verifies DELETE works when cursor starts
// at position 0 (no prior typing). This was the core bug where transitionToEditing
// would reload editBuf after the deletion.
func TestDeleteSingleChar_InitialCursor(t *testing.T) {
    doc, _ := document.NewDocument("a")
    m := New(doc)
    // Cursor at position 0, on the 'a' - no typing happened
    m2, _ := m.Update(tea.KeyMsg{Type: tea.KeyDelete})
    if m2.editBuf != "" {
        t.Errorf("Expected editBuf='' after DELETE at position 0, got %q", m.editBuf)
    }
}
```

**Critical detail from model.go lines 850-855:**

### Anti-Patterns to Avoid
- **Don't fix without failing test:** Always write the test first to prove the bug exists
- **Don't test TUI with unit tests:** Use catwalk for TUI, not mocked tea.Msg sequences
- **Don't assume the bug location:** convert_rate "preview" bug could be in interpreter OR display formatting
- **Don't test multiple bugs in one test:** Each bug scenario gets its own test case

## Common Pitfalls

### Pitfall 1: editBuf State Confusion
**What goes wrong:** After DELETE, editBuf gets reloaded from document, undoing the deletion
**Why it happens:** transitionToEditing() reloads editBuf if empty, called AFTER deletion logic
**How to avoid:** Always call transitionToEditing() BEFORE modifying editBuf
**Warning signs:**
- Test passes in isolation but fails in real TUI
- Debounce timer causes test to fail
- editBuf contents differ between Update calls

**Root cause from model.go line 853:**
```go
// CRITICAL: Must be called first, because transitionToEditing reloads
// editBuf if it's empty, which would undo any deletion.
m.transitionToEditing()
```

### Pitfall 2: KB vs kb Interpretation Ambiguity
**What goes wrong:** User writes "50kb" expecting 50,000 bytes but gets 51,200 bytes (50 * 1024)
**Why it happens:** normalize.go line 163 maps both "kb" and "KB" to binary kilobytes (1024-based)
**How to avoid:** This is a design choice, not a bug. Document clearly in help system.
**Warning signs:**
- User reports "50kb displays as 48.8 KB" (actually 50 binary KB = 51,200 bytes, normalized to 50 KB)
- Confusion between decimal (1000) and binary (1024) interpretations

**Technical detail from normalize.go lines 154-163:**
```go
// Data Storage (binary, base: byte)
dataStorage := &UnitFamily{
    BaseUnit: "bytes",
    Units: []UnitScale{
        {"bytes", d("1")},
        {"KB", d("1024")},  // Binary interpretation
        {"MB", d("1048576")}, // 1024^2
        // ...
    },
}
registerFamily("data_storage", dataStorage, map[string][]string{
    "KB": {"kb", "KB", "kilobyte", "kilobytes"},  // Both map to binary
```

**Industry context:** IEC 80000-13 (2008) standardized KiB for binary (1024) and KB for decimal (1000), but software practice varies widely. Windows uses binary, macOS uses decimal since Snow Leopard.

### Pitfall 3: Preview Pane Showing Non-Result Content
**What goes wrong:** Blockquotes, links, and other markdown render in Results pane
**Why it happens:** Preview pane renders entire TextBlock without filtering
**How to avoid:** Filter preview content in aligned.go computeAlignedPanes() to show only calc results
**Warning signs:**
- "> quote text" appears in Results pane
- [link text](url) renders in preview
- Only headings and calc results should show

**Architecture from block_render.go:**
- TextBlock rendered via RenderTextBlockAligned()
- Markdown rendered via glamour (MarkdownRenderer)
- Need filter layer between rendering and display

### Pitfall 4: convert_rate Display vs Calculation Bug
**What goes wrong:** convert_rate(10 mb/s, per hour) shows wrong result in preview
**Why it happens:** Could be interpreter calculation OR display formatting
**How to avoid:** Test both layers independently before fixing
**Warning signs:**
- Unit test for convert_rate passes but TUI shows wrong value
- FormatRate() produces unexpected output
- Rate type not preserving correct per-unit value

**Investigation checklist from todo:**
1. Check what convert_rate returns (interpreter test)
2. Verify Rate type formatting in FormatRate() (display test)
3. Check if "per hour" is correctly parsed (semantic test)

```go
func TestFeature(t *testing.T) {
    tests := []struct {
        name     string
        input    string
        expected string
    }{
        {"positive case", "input1", "output1"},
        {"negative case", "input2", "output2"},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            t.Helper() // Mark as helper for accurate error reporting

            result := FeatureFunc(tt.input)
            if result != tt.expected {
                t.Errorf("got %q, want %q", result, tt.expected)
            }
        })
    }
}
```

## Open Questions

Things that couldn't be fully resolved during research:

1. **Is "50kb displays as 48.8 KB" a bug or user misunderstanding?**
   - What we know: normalize.go uses binary KB (1024), user might expect decimal (1000)
   - What's unclear: User intent when writing "kb" (lowercase) - binary or decimal?
   - Recommendation: Investigate if user actually wrote "50kb" or if it's a different issue. Binary interpretation is correct by design.

2. **Where exactly does preview pane markdown filtering happen?**
   - What we know: block_render.go renders markdown, aligned.go builds preview lines
   - What's unclear: Which component decides "only show results and headings"?
   - Recommendation: Trace preview rendering in aligned.go computeAlignedPanes() method

3. **Is convert_rate bug in interpreter or display layer?**
   - What we know: User reports incorrect preview result for convert_rate(10 mb/s, per hour)
   - What's unclear: Does interpreter return wrong Rate value, or does FormatRate() display it wrong?
   - Recommendation: Write tests for both layers before investigating code
