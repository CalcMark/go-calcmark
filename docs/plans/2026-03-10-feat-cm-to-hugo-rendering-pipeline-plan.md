# feat: CalcMark-to-Hugo Full Document Rendering Pipeline

## Overview

Build a pipeline that converts `.cm` example files into fully evaluated Hugo pages at
build time. Each worked example on calcmark.org gets a "View full document" link at the
top, pointing to a child page (`/full/`) that shows the complete CalcMark file with
computed results inline — rendered via `cm convert --to md` output as a plain Hugo
markdown page.

## Problem Statement / Motivation

Today, worked example pages show curated excerpts with prose explanations. The backing
`.cm` file is only accessible via a GitHub link and `cm remote` copy command. Readers
who want to see the full document — with all calculations evaluated — must clone the
repo and run `cm` locally. This gap means the site doesn't showcase CalcMark's most
impressive output: a complete, evaluated document.

## Proposed Solution

### Phase 1: Page Bundle Migration (prerequisite)

Existing example pages are flat files (`services-pl.md`). Hugo requires a **page bundle**
structure for subpages to work: `services-pl/index.md` + `services-pl/full.md`.

Migrate all 15 example pages from `<name>.md` → `<name>/index.md`. This is a
structural-only change — content is identical, URLs are preserved.

**Files changed:**
- `site/content/docs/examples/*.md` → `site/content/docs/examples/*/index.md`

**Verification:** `task site:build` produces identical output (diff the `public/` directory).

### Phase 2: Hugo Archetype

Create `site/archetypes/worked-example.md` to enforce the required structure for all
worked example pages.

```yaml
---
title: "{{ replace .Name "-" " " | title }}"
summary: ""
weight: 0
calcmark_build: progressive
calcmark_source: "testdata/examples/{{ .Name }}.cm"
---

The complete CalcMark file is available at {{</* repo-file path="" */>}}.

---

<!-- Walkthrough content goes here -->
```

**Usage:** `hugo new --kind worked-example content/docs/examples/<name>/index.md`

**What it enforces:**
- `calcmark_build: progressive` — all code blocks share interpreter context
- `calcmark_source` — explicit path to the backing `.cm` file
- Body skeleton with the `repo-file` shortcode placeholder

### Phase 3: Extend `cmd/doceval`

Add a new phase to doceval that runs **after** the existing code-block evaluation:

#### 3a. Parse `calcmark_source` from frontmatter

Extend the existing line-by-line frontmatter scanner alongside `calcmarkBuildMode()`.
Add a `calcmarkSource()` function that extracts the `calcmark_source:` value.

- Strip surrounding double quotes from the value (the archetype template uses quotes).
- Return empty string if the field is absent (page is skipped for full-doc generation).

```go
// cmd/doceval/main.go
func calcmarkSource(content string) string {
    // Same pattern as calcmarkBuildMode: scan between --- delimiters
    // Look for "calcmark_source:" line, extract value, trim quotes
}
```

#### 3b. Evaluate `.cm` files and write `full.md`

For each page with a non-empty `calcmark_source`:

1. Resolve the path relative to the repo root.
2. Read and evaluate the `.cm` file using the library directly (consistent with existing
   doceval pattern — `document.NewDocument` + `implDoc.NewEvaluator`).
3. Format via `MarkdownFormatter` with a new option to render CalcMark frontmatter as a
   ` ```yaml ` code fence instead of raw `---` delimiters (avoids Hugo frontmatter
   collision — see Technical Considerations).
4. Prepend Hugo frontmatter:
   ```yaml
   ---
   title: "<parent page title> — Full Document"
   # generated by doceval — do not edit
   _build:
     list: never
   ---
   ```
   The `_build.list: never` tells Hugo to render the page but exclude it from section
   listings and sitemaps.
5. Write to `site/content/docs/examples/<name>/full.md`, creating the directory if needed
   via `os.MkdirAll`.

#### 3c. Skip generated files during walk

doceval walks `site/content/**/*.md` for block evaluation. Generated `full.md` files
contain calcmark code fences from MarkdownFormatter output. To avoid re-evaluating them:

- Skip any file whose Hugo frontmatter contains `# generated by doceval`.
- This check runs during the existing walk phase, before block extraction.

#### 3d. Error handling

- **Missing `.cm` file:** Fail the build with a clear error message. `calcmark_source` is
  an explicit author declaration — a missing file is a broken reference.
- **Evaluation failure:** Fail the build (consistent with progressive mode strictness).
- **Page without `calcmark_source`:** Silently skip (no full-doc generation).

### Phase 4: Hugo Layout — "View Full Document" Link

Add a conditional in `site/layouts/_default/page.html` (or a new partial) that reads
`calcmark_source` from frontmatter. When present, render a "View full document →" link
before the page content.

This is layout-driven, not inline markdown — so authors don't need to manually add the
link, and existing pages get it automatically once `calcmark_source` is in their
frontmatter.

Also add a "← Back to walkthrough" link on `full.md` pages (detected via the
`# generated by doceval` comment or a dedicated frontmatter field).

## Technical Considerations

### CalcMark Frontmatter vs. Hugo Frontmatter Collision

The MarkdownFormatter serializes CalcMark frontmatter (globals, exchange rates) as a
`---...---` YAML block. If doceval prepends Hugo frontmatter, Hugo sees two frontmatter
blocks and misparses the page.

**Solution:** Add a `SkipRawFrontmatter bool` option to `format.Options`. When true,
MarkdownFormatter renders CalcMark frontmatter as a visible ` ```yaml ` code fence
instead of raw `---` delimiters. This preserves the information visually while avoiding
the Hugo collision.

```go
// format/options.go or format/formatter.go
type Options struct {
    // ...existing fields...
    SkipRawFrontmatter bool // render CM frontmatter as code fence, not ---
}
```

### Hugo Template Argument Order

Hugo template functions take arguments in reverse order vs. Go stdlib. From past
learnings: `strings.TrimRight " \t" .` (correct) vs. `strings.TrimRight . " \t"` (wrong).
Keep this in mind for any new template logic.

### Performance

doceval evaluates each `.cm` file once via the interpreter library. With 10 files, this
adds seconds to the build, not minutes. No caching needed beyond Taskfile's source/generates
checking.

## Dependencies & Risks

**Dependencies:**
- Phase 1 (page bundle migration) must complete before any other phase
- Phase 3b depends on the MarkdownFormatter option from Technical Considerations
- Phase 5 depends on Phase 3 (doceval must be working before migration produces results)

**Risks:**
- Page bundle migration could break cross-references or shortcodes in existing pages. Mitigated by diffing `public/` output before and after.
- Hugo dev server (`task site`) does not auto-regenerate `full.md` when `.cm` files change. This is a known limitation — document it in doceval README. Authors must re-run `task generate-docs` manually.
